## 1. 目标与非目标

### 1.1 目标

- 前端运营看板能够调用后端真实接口（`/events`、`/events/{id}`、`/events/{id}/timeline`、`/metrics`、`/events/{id}/approval`），正确渲染数据。
- 解决跨域问题，使前端开发服务器（localhost:8080）能与后端（localhost:8000）正常通信。
- 修复前端点击事件导致右侧详情无法切换的 Bug。

### 1.2 非目标

- 不涉及后端业务逻辑修改。
- 不涉及前端 UI 重构或新增功能。
- 不涉及生产环境部署。

## 2. 职责与边界

- 本模块负责：前端页面与后端接口的对接、跨域配置、前端交互逻辑修复。
- 本模块不负责：后端接口的正确性、数据生成、审批流程的业务逻辑。
- 需要人工参与的环节：后端启动后需手动调用 `POST /runs` 生成测试数据（或在 Swagger 中执行）。

## 3. 输入与输出

### 3.1 输入

| 字段/对象 | 类型 | 必填 | 来源 | 含义与约束 |
|---|---|---|---|---|
| 后端 Base URL | string | 是 | 环境配置 | `http://127.0.0.1:8000` |
| 事件列表 | JSON Array | 是 | GET /events | 事件 ID、标题、状态等 |
| 事件详情 | JSON Object | 是 | GET /events/{id} | 告警、研判、调查、处置 |
| 时间线 | JSON Array | 是 | GET /events/{id}/timeline | 状态变更记录 |
| 指标 | JSON Object | 是 | GET /metrics | total_events 等 |
| 审批请求 | JSON Object | 是 | POST /events/{id}/approval | 审批意见、审批人 |

### 3.2 输出

| 字段/对象 | 类型 | 去向 | 含义与约束 |
|---|---|---|---|
| 页面渲染 | HTML/CSS/JS | 用户浏览器 | 展示事件列表、详情、时间线、指标 |
| 审批响应 | JSON | 前端回调 | 显示审批成功/失败消息 |

## 4. 核心流程与状态变化

1. 用户打开页面 → 前端调用 `GET /events` 获取事件列表 → 渲染左侧列表。
2. 用户点击某事件 → 前端调用 `GET /events/{id}` 和 `GET /events/{id}/timeline` → 渲染右侧详情和时间线。
3. 页面加载时自动调用 `GET /metrics` → 渲染顶部指标卡片。
4. 用户点击"审批"按钮 → 弹出审批弹窗 → 提交 `POST /events/{id}/approval` → 显示结果并刷新列表。

状态变化：事件状态（open → in_progress → resolved 等）由后端控制，前端仅展示。

## 6. 安全边界

- 权限与审批：前端仅展示审批按钮，后端负责鉴权（当前 MVP 无鉴权）。
- 输入校验：前端对审批表单进行非空校验，后端负责格式校验。
- 敏感信息处理：前端不存储敏感数据，展示时脱敏（IP、主机名等替换为 `***`）。
- 失败、超时与人工接管：后端不可用时前端自动降级为演示模式（Mock 数据）。
- 真实执行与Mock边界：联调时使用真实后端数据，Mock 数据仅用于演示模式。

| 决策 | 原因 | 未采用方案及原因 |

## 4. 核心流程与状态变化

1. 页面加载 → `loadAll()` 并发请求 `/events` 与 `/metrics`。
2. 根据 `backendAvailable` 标志决定使用真实数据还是降级：
   - **两个接口都失败** → 降级到 `demo-data.js`，`usingDemo = true`。
   - **任一成功** → 视为后端可用，使用后端数据（允许空数组）。
3. 渲染完成后调用 `updateSourceTag()` 判定来源标签。
4. 用户点击事件行 → `renderDetail()` 拉取详情 → 展示五段式时间线。
5. 用户点击「审批」→ 弹窗填写 → `POST /approval` → 刷新详情。
6. 异常路径：`jfetch` 捕获超时（AbortError）/ 网络错误 / HTTP 非 2xx → 返回 `null` → 触发降级或不静默填充。

### 状态迁移

| 当前状态 | 目标状态 | 触发条件 |
|---|---|---|
| INVESTIGATING | APPROVAL_REQUIRED | 研判完成需人工审批 |
| APPROVAL_REQUIRED | COMPLETED | 审批通过（approved=true） |
| APPROVAL_REQUIRED | FAILED | 审批拒绝（approved=false） |
| 任意 | FAILED | 处理过程中出错 |

## 5. 数据来源标识设计

### 5.1 标识原则

页面右上角设“数据来源”标签，其取值**严格依据后端响应字段**（`sample_nature` 优先，缺省时取 `source`），不外推、不猜测。四类来源语义明确区分：

| 后端字段值（`sample_nature` / `source`） | 标签文案 | 语义 |
|---|---|---|
| `real_xdr` | 数据来源：真实 XDR 数据 | 来自真实平台的事件数据 |
| `fixed_sample` | 数据来源：固定样例 | 后端主动返回的 Mock 样例 |
| `fixed_sample_fallback` | 数据来源：固定样例（回退） | 本想取真实数据但因故退回固定样例 |
| `demo` | 数据来源：演示数据 | 后端返回的演示性质数据 |
| 前端降级（`usingDemo=true`） | 数据来源：演示数据（前端降级） | 后端完全不可用，前端自行回退 |
| 其他未知值 | 数据来源：<原始值> | 兜底，明文展示原始字段 |

### 5.2 判定优先级

`updateSourceTag()` 的判定顺序如下：

1. **前端降级优先**：若 `usingDemo === true`（即 `/events` 与 `/metrics` 均失败），一律显示为“演示数据（前端降级）”，与后端返回的任何 `demo` 数据区分开。
2. **取判定依据**：以列表首条事件 `events[0]` 的 `sample_nature` 或 `source` 字段为准。
3. **枚举匹配**：按 5.1 表格映射为对应文案；命中未知值时直接展示原始值。

> **说明**：标签依据列表第一条事件判定，因此当批量列表中混入多种来源时，标签仅代表首条事件的性质。若后续支持混合来源，应改为在事件行内逐行标注。

## 6. 降级边界设计（demo-data.js）

### 6.1 触发条件

仅在以下同时满足时降级：

- `/api/events` 请求失败（返回 `null`）；
- `/api/metrics` 请求失败（返回 `null`）；

即**双接口均失败**才设置 `usingDemo = true` 并加载 `demo-data.js`。

### 6.2 不触发降级的情形

下列情形均视为“后端可用”，**不**静默使用演示数据：

- 任一接口正常返回（含空数组 `[]`）；
- 接口返回 401 / 403 / 其他 HTTP 非 2xx（此时 `jfetch` 返回 `null`，但 `loadAll` 依据双接口判定，`usingDemo` 仍为 `false`）；
- 详情接口 `/events/{event_id}` 失败但列表接口正常：此时 `renderDetail` 仅展示“加载详情失败，请稍后重试”，不从 `DEMO_EVENTS` 静默填充。

### 6.3 降级表现

触发后，列表与指标均使用 `window.DEMO_EVENTS` / `window.DEMO_METRICS`，并在右上角显示“演示数据（前端降级）”提示，明确告知用户当前为降级态。

## 7. 异常处理设计

- **超时**：`jfetch` 内置 10 秒 `AbortController`，超时主动中断并返回 `null`，由 `loadAll` 汇总判定是否降级。
- **鉴权失败**：401 / 403 时弹窗提示“登录已失效，请重新登录”（本轮仅 alert，不跳转登录页）。
- **空结果**：列表为空数组时渲染“暂无事件数据”占位，指标为空时各卡片显示 `--`。
- **局部 Fallback**：单个组件（如时间线、卡片）渲染异常不影响页面整体，由全局兜底统一处理。
- **全局兜底**：`window.onerror` 捕获未处理异常，展示“系统繁忙，请稍后重试”及重新加载按钮，避免白屏。

| 上游 | 后端 REST API | `sec_agent/api/routes/events.py` | 已对齐 |

## 9. 安全边界

- **权限与审批**：`APPROVAL_REQUIRED` 必须通过弹窗显式提交，含 `idempotency_key` 防重放。
- **输入校验**：`escapeHtml` 对所有动态文本转义，防止 XSS。
- **敏感信息处理**：前端不存储 Token、密码、内网地址；演示数据为人工构造，不含真实平台数据。
- **失败、超时与人工接管**：见第 6、7 节。
- **真实执行与 Mock 边界**：通过 `source` / `sample_nature` 字段区分，标签明文展示，绝不混用。

## 10. 关键设计决策

| 决策 | 原因 | 未采用方案及原因 |
|---|---|---|
| **双接口都失败才降级** | 避免单个接口短暂异常误触发降级，提升稳定性 | 旧逻辑“任一失败即降级”过于敏感 |
| **`backendAvailable` 标志** | 准确区分“后端完全不可用”与“部分数据为空”，防止详情接口静默填充演示数据 | 仅靠 `usingDemo` 无法区分回退场景 |
| **来源标签四态判定** | `real_xdr` / `fixed_sample` / `fixed_sample_fallback` / `demo` 各有语义，用户无需猜测 | 旧版仅“真实/演示”两态，无法表达“想取真实却回退”的中间态 |
| **`usingDemo` 与 `demo` 字段分开** | 前端自行降级与后端返回的演示数据性质不同，标签必须区分 | 合并处理会使用户误判数据来源 |
| **10 秒超时 + AbortController** | 防止后端挂起导致页面永久 loading | 无超时则 fetch 会无限等待 |
| **`row.dataset.id` 显式赋值** | 修复点击行空白区域无法打开详情的 bug | 依赖 `event.target.dataset` 在点击空白时取到 undefined |
| **`renderMetrics` 空值保护** | `metrics` 为 null 时显示 `--`，避免 Cannot read properties of null | 旧代码直接访问 `metrics.xxx` 报错 |
| **全局错误兜底 `window.onerror`** | 未捕获异常时展示“系统繁忙”而非白屏 | 默认行为为控制台报错 + 白屏 |
